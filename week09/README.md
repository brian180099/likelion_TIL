# 📘 Today I Learned

### 1. 오늘 배운 내용
- Supabase를 사용해서 프론트엔드 앱의 데이터를 브라우저 상태가 아니라 외부 데이터베이스에 저장하는 방법을 배웠다.
- `@supabase/supabase-js`로 명단 데이터를 조회하고, 로그인한 사용자만 추가와 삭제를 할 수 있도록 CRUD 흐름을 구현했다.
- 이메일/비밀번호 기반 회원가입, 로그인, 로그아웃을 Supabase Auth로 연결했다.
- `.env.local`과 `VITE_` 접두사를 사용해 Supabase URL과 anon key를 코드에 직접 노출하지 않는 방법을 정리했다.
- RLS(Row Level Security)를 켜고 정책을 설정하면, 클라이언트에서 직접 DB에 접근하더라도 권한을 안전하게 분리할 수 있다는 점을 배웠다.

### 2. 핵심 정리 (내 언어로)
- 지금까지는 새로고침하면 사라지는 React 상태에 데이터를 저장했지만, 이번에는 Supabase DB에 저장해서 브라우저를 닫거나 다른 기기에서 접속해도 같은 명단을 볼 수 있게 만들었다.
- 로그인하지 않은 사용자는 명단을 볼 수만 있고, 로그인한 사용자만 명단을 추가하거나 삭제할 수 있게 했다. 실제 서비스에서 “읽기 권한”과 “수정 권한”을 나누는 이유를 더 분명하게 이해했다.
- Supabase 클라이언트에는 `Database` 타입을 연결하고, DB Row 타입을 앱에서 쓰는 `Lion` 타입으로 바꾸는 함수를 따로 만들었다. 이렇게 하니 서버 데이터 구조와 화면에서 쓰는 데이터 구조를 구분해서 관리할 수 있었다.
- URL 쿼리 파라미터로 검색, 필터, 정렬, 보기 옵션을 유지해서 SPA 안에서도 사용자가 선택한 화면 상태가 주소에 남도록 했다.
- 환경 변수와 `.gitignore` 설정도 기능만큼 중요하다는 것을 느꼈다. API 키를 코드나 GitHub에 올리지 않는 습관이 필요하다.

### 4. 느낀 점
- Supabase를 붙이면서 프론트엔드만으로도 꽤 실제 서비스에 가까운 흐름을 만들 수 있다는 점이 신기했다.
- 단순히 화면에 카드를 추가하는 것과, DB에 저장하고 인증 상태에 따라 버튼을 잠그는 것은 완전히 다른 문제라는 걸 느꼈다.
- 에러, 로딩, 비로그인 안내 같은 상태를 챙기니까 사용자가 지금 무엇을 할 수 있는지 더 명확해졌다.
- 다음에는 실제 Supabase 프로젝트의 데이터를 더 많이 넣어 보고, 내가 만든 RLS 정책이 의도대로 동작하는지도 여러 계정으로 테스트해 보고 싶다.
